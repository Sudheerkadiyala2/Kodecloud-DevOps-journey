# Day 50: Implement the Sidecar Pattern for Nginx Log Aggregation

**Date:** 2026-06-20  
**Platform:** KodeKloud DevOps 100 Days Challenge  
**Category:** Kubernetes Multi-Container Pods

## Challenge

The Nautilus DevOps team required implementation of the **Sidecar Pattern** to handle Nginx log aggregation within a Kubernetes Pod.

Instead of storing logs on persistent storage, a secondary container would continuously read and process Nginx access and error logs from a shared volume.

### Requirements

- Create a Pod named `webserver`.
- Create an `emptyDir` volume named `shared-logs`.
- Create a main container:
  - Name: `nginx-container`
  - Image: `nginx:latest`
- Create a sidecar container:
  - Name: `sidecar-container`
  - Image: `ubuntu:latest`
- Configure the sidecar container with the command:

```bash
sh -c "while true; do cat /var/log/nginx/access.log /var/log/nginx/error.log; sleep 30; done"
```

- Mount the shared volume in both containers at:

```text
/var/log/nginx
```

- Ensure all containers remain active and healthy.

---

## Solution

### Step 1: Create the Pod Manifest

Create a file named `pod.yaml`.

```bash
vi pod.yaml
```

Add the following configuration:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: webserver
spec:
  initContainers:
  - name: sidecar-container
    image: ubuntu:latest
    restartPolicy: Always
    command:
    - sh
    - -c
    - while true; do cat /var/log/nginx/access.log /var/log/nginx/error.log; sleep 30; done
    volumeMounts:
    - name: shared-logs
      mountPath: /var/log/nginx

  containers:
  - name: nginx-container
    image: nginx:latest
    volumeMounts:
    - name: shared-logs
      mountPath: /var/log/nginx

  volumes:
  - name: shared-logs
    emptyDir: {}
```

## Troubleshooting Encountered

### YAML Syntax Error

Initial deployment failed with:

```text
error parsing pod.yaml:
yaml: line XX: did not find expected key
```

Resolution:

- Reviewed the YAML structure.
- Corrected indentation and formatting issues.
- Reapplied the manifest successfully.

### Init Container Blocking Issue

A standard init container waits to complete before starting application containers. Since the required sidecar command runs indefinitely, the main Nginx container would never start.

To satisfy the lab requirements while keeping the sidecar active, the following configuration was used:

```yaml
restartPolicy: Always
```

inside the init container definition, allowing Kubernetes to keep the sidecar running while permitting the Nginx container to start normally.

## Key Concepts Learned

### Sidecar Pattern

The Sidecar Pattern deploys an auxiliary container alongside the main application container.

Benefits:

- Separation of concerns.
- Centralized log processing.
- Independent responsibilities.
- Shared networking and storage.

### emptyDir Volume

The `emptyDir` volume:

- Is created when the Pod starts.
- Is shared among containers in the same Pod.
- Persists for the lifetime of the Pod.
- Is ideal for temporary log storage and container communication.

### Shared Log Processing

Both containers mounted:

```text
/var/log/nginx
```

allowing the sidecar container to continuously access and process the same log files generated by the Nginx web server.

## Outcome

Successfully implemented the Kubernetes **Sidecar Pattern** by deploying an Nginx application container alongside a log-shipping sidecar container. Both containers shared the **shared-logs** emptyDir volume, enabling real-time log access and aggregation while maintaining a clean separation of responsibilities within the Pod.
